# 複数Issueを進める会話と記録の例

やりたいことや優先順位は具体的に指示できます。次に進める作業の選択を任せたいときは、「進めてください」でも、AIが担当・承認・依存を確認して進めます。未提示の設計や新しい権限への同意まで含む依頼ではありません。

この文書の会話・Issue番号・時刻・結果は**説明用の架空例**です。番号は実際に発行したものではなく、試用の成功記録でもありません。実作業ではGitHubが発行した番号と実際の確認結果に置き換えます。

## 誰が何をするか

| 担当 | 行うこと |
| --- | --- |
| 人間 | 作るもの・優先順位を伝え、必要な設計・分担・権限の提案を判断する。PRの内容と根拠を確認し、マージを判断する |
| AIの統合担当 | 設定・環境能力・全候補・既存作業を照合し、許可されたIssueを選ぶ。検証・組合せ確認・保存・報告をまとめる |
| 各IssueのAI | 自分のブランチで実装・検証し、IssueごとにPRを準備する。別の会話・実行環境で動くAIがレビューする |
| 検査コードとCI | 設定や計画・記録の形式/整合、採用したテストとセキュリティ検査を確認する。AIの実行自体は利用する開発サービスが管理する |

コードの検査成功は、設計の承認・実サービスの残量取得・強制停止・人間のレビューを代行しません。アプリ自身のテストは、テンプレート運用の検査と別に選びます。

## 1. 継続依頼から候補を選ぶ

**人間**：「進めてください」

AIは[既定設定](../../../.ai-workflow/autonomy.yaml)を読み、[設定検査](../../common/workflow-tools-guide.md#autonomy-settings)と、担当・ready-for-ai・当該工程の承認・依存・既存ブランチ/PR・着手記録を確認します。ready-for-aiだけでは自動着手の許可や排他制御になりません。

架空例では全候補が同じ人間ownerの担当であり、照合した結果は次のとおりとします。

| 説明用Issue | 確認結果 | AIの選択 |
| --- | --- | --- |
| 1001：検索の改善 | ready、具体設計承認済み、依存なし、重複着手なし | 着手候補 |
| 1002：通知文の改善 | ready、具体設計承認済み、1001と変更領域・意味上の依存なし | 着手候補 |
| 1003：権限の追加 | 設計判断待ち | 保留 |
| 1004：管理画面 | 1003のマージに依存 | 下流も待機 |

既定値は**総2 Issue・60分・同時開発1件・Issueごと修正2巡**で、最後の10分は保存・報告に使います。保留・失敗でも工程へ着手したIssueは総数から除外しません。候補一覧を読むだけなら着手数には加えません。通常は1001、1002を順次進められ、人間が毎回次のIssueを選ぶ必要はありません。

## 2. 並行で進める場合だけ具体的な分担を確認する

この例では、両Issueの独立性と、複数AIの起動・状態確認・停止・独立レビュー能力を確認できたとします。

**AI**：「1001と1002を別ブランチで並行して進める案です。私が統合担当、AI-Aが検索部分、AI-Bが通知文を担当します。共有API・設定・他Issueは変更しません。互いの成果をレビューし、私が最新mainと両PRの組合せを確認します。今回は同時開発2件・最大3エージェントとし、総2件・60分・修正2巡は維持します。消費増や共有領域への影響は、上限と担当分離で抑えます。この分担でよいですか？」

**人間**：「この分担で進めてください」

実際の提案には変更可能なファイル一覧・触らない範囲・検証方法も含めます。同じ承認は繰り返し求めません。今回だけの並列2件は記録へ残し、既定設定は変えません。機能や承認がなければ順次進めます。worktreeはGit作業の分離であり、権限や通信の隔離ではありません。

## 3. AIがGitHubへ開始・途中保存を記録する

依頼を受けて進める1回の作業をrunと呼びます。人間の記入は不要で、AIが[記録様式](../../common/operations-reference.md#continuation-records)でIssueへ保存します。開始記録の正本URLを各Issueから参照します。

以下も架空の記入例です。`<M>`・`<H1>`等はcommitやURLの代わりに置いた記号で、実在する証拠ではありません。実記録には完全なcommit・実URLを使い、未確認の値を推測で補いません。

```text
run: example-run-1 / owner: example-owner
許可工程: Issue1001/1002の設計承認記録、上記の並列分担承認
開始: 2030-01-01T10:00:00Z / 新規開始停止: 10:50Z / 期限: 11:00Z
設定: <M>のautonomy.yaml revision1、静的検査成功という例
今回指定: 人間が同時開発2件を承認 / 他の上限は既定値を維持
実効上限: 総2 Issue・60分・並列2・修正2巡・保存余裕10分・残量30/15%
能力: 時刻/編集/検査/保存と読戻し/agent状態と停止/独立レビューが利用可能という例
残量: 不明（最初から取得非対応）。件数・時間方式、機械監視・強制停止なし
累積: 着手1001/1002の2件、修正は各0巡、統合担当+AI-A+AI-Bの3agent
作業: 1001 branch feature/example-1001、1002 branch feature/example-1002
両branchの確認head: <M>、PRなし、未commit/未push差分なし、未確認作業なし
次: 各Issueの承認済み範囲を実装・検証する
```

工程の区切りでは同じrunへ追記し、commit/push・PR・投稿を読み戻します。設定検査の成功は、今回指定との合成や実停止の証拠にはしません。秘密・環境値・モデル入出力の原文は公開しません。

```text
run: example-run-1 / 正本: <開始記録URL> / 保存確認: 2030-01-01T10:25:00Z
設定/期限: 開始記録から変更なし。着手2件、修正1001=1巡/1002=0巡
稼働: 統合担当+AI-A+AI-Bの3agent、未確認作業なし
1001: feature/example-1001、local/remote head <H1>、<PR-A URL>、未commit/未pushなし
1002: feature/example-1002、local/remote head <H2>、<PR-B URL>、未commit/未pushなし
検証: 各headの対象テスト成功という例（実ログは<検証記録URL>）
AIレビュー: 未実施 / 各PRのCI: 実行中 / 組合せ確認: 未実施
残量: 取得非対応で不明 / 停止理由: なし（途中保存）
次: AI-Aが1002、AI-Bが1001をread-onlyでレビュー。指摘は元の実装担当が修正
```

投稿やpushの応答が不明なら、再送前に実態を読み戻します。保存できなければ後続Issueを始めず、最後の確認済み地点と未公開作業を報告します。

## 4. 検証して報告し、人間のマージを待つ

各Issueのテスト・セキュリティ検査・実装者とは別のAIによるレビューを行い、対象commit（head）と結果を記録します。指摘は元のブランチで修正し、新headを再確認します。統合担当は最新mainと両headを固定して、競合・共有契約・必要なtest/buildを確認します。main/headが変われば組合せを再確認します。

必須検査・独立レビュー・組合せ確認が未実施ならdraftまたは待機です。自己確認で独立レビューを代用しません。採用済みCIは維持し、細かい指示ごとの検査は[検査時点の規約](../../common/operations-reference.md#security-review-timing)に従います。

架空例の終了報告は、実施済みと未実施を分けて次のように残します。

```text
run: example-run-1 / 正本: <開始記録URL> / 保存確認: 2030-01-01T10:45:00Z
状態: 人間のレビュー/マージ待ちで終了
設定/期限: 開始記録から変更なし / 着手2件、修正1001=1巡/1002=0巡
agent: 両実装担当の作業停止を確認、未確認作業なし
成果: 1001=<PR-A URL>/<H1>、1002=<PR-B URL>/<H2>、両方未commit/未pushなし
検証: 各headの対象テスト/必要Security/CI成功という例（<各結果URL>）
独立レビュー: H1をAI-B、H2をAI-Aが確認、指摘解消という例（<レビュー記録URL>）
組合せ: main<M>+H1+H2の競合/契約/必要テスト確認成功という例（<結果URL>）
実施範囲: 上記は架空の記入例であり、この文書による実証なし
合成確認: 残量30%/15%の判定試験がある場合は、その入力と結果を別記
未実証: 実残量による停止、サービス強制中断からの復旧、全環境での並列動作
残量: 不明（取得非対応）/ 停止理由: 許可候補2件をPRにし、人間判断待ち
次: 人間がPR内容と根拠を確認。依存なしのため推奨マージ順1001→1002
保留: 1003は設計判断待ち、1004は1003のマージ待ち。勝手に完了扱いしない
```

PRを作っただけでは依存完了になりません。人間がマージしたらAIが読み戻し、残る下流候補・上限・承認を確認します。報告は朝や定刻まで待たず、区切りで行います。

## 5. 途中で再接続した場合

10:25の保存点で会話が再接続した場合、AIは元記録と担当・承認・main/PR head・未公開差分・稼働agentを照合します。**同じrunなら10:00開始/11:00期限・着手2件・修正巡回を維持**します。状況質問・再接続・コンパクションで枠をリセットしません。不明な累積や旧作業は確認まで新規開始を止めます。

50分以降は新しいIssue・agent・修正巡回を始めず、保存と報告を優先します。利用枠の取得口が故障した場合は、最初から非対応だった場合へ読み替えず、新規停止して1回まで再確認し、回復しなければ保存停止します。突然の利用制限では最終保存できない場合もあります。

run終了後に人間が改めて「進めてください」と依頼した場合は、条件を確認して新runを記録できます。未完了Issueを今回の件数に含め、未解決指摘とIssue別の修正巡回を引き継ぎます。AIがrunを自動連結して上限を迂回することはありません。

詳しい条件は[継続依頼の手順](../../common/development-rules.md#continuation-procedure)と[設定・停止・再開の設計](../../common/native-continuation-design.md)、人間の確認箇所は[運用マニュアル](../../common/operations-manual.md)を参照してください。
