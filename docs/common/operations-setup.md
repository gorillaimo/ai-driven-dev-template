# 初期セットアップ

**人間は目的と担当者を伝え、AIに準備を任せます。IssueもAIが作成できます。**
このページでは、最初の依頼と人間が判断する点を説明します。コマンドや設定ファイルの詳細は、AIが[設定資料](operations-reference.md#setup-details)と[検査ツール](workflow-tools-guide.md)を参照します。

## 1. 人間が用意すること

- 対象のリポジトリをAI開発ツールで開きます。新規の場合は、このテンプレートから作成したものを使います。
- やりたいことと、責任を持つ人間のGitHubアカウントを伝えます。
- AIが対象ファイルを編集し、GitHubのIssueを読み書きできる接続を用意します。接続・権限が不足する場合は、AIが必要な操作を案内します。

リポジトリ自体の作成もAIへ依頼できます。その場合はowner・リポジトリ名・公開範囲を決めて伝えます。既存のリポジトリを使う場合は追加の作成依頼は不要です。

## 2. 最初に送る依頼

### 新しいプロジェクト

```text
このテンプレートで新規開発の準備を進めてください。
作りたいもの: ［概要］
人間の担当者: ［GitHubアカウント］
必要なIssueの作成から任せます。
```

### 既存プロジェクトへ導入する場合

```text
この既存プロジェクトへAI駆動開発テンプレートを導入したいです。
人間の担当者: ［GitHubアカウント］
調査Issueの作成から進め、既存のコードや設定は保持してください。
```

既存プロジェクトへ取り込むテンプレートの場所・versionが分からない場合は、AIが確認します。
**人間が先にIssueを作る必要はありません。** AIが既存Issueとの重複を確認し、目的・範囲・受け入れ条件などを整理してGitHubへ発行します。既にIssueがある場合は、その番号を渡せます。
依頼した人間を担当に設定し、必要な着手条件を確認します。別の担当者や進行中の作業がある場合は、AIが調整を求めます。

依頼後は、質問や提案に答えながら「進めてください」で続けます。

## 3. 依頼を受けたAIが進めること

| 順序 | AIが行うこと | 人間に確認する点 |
| :--- | :--- | :--- |
| 準備 | AGENTS.md・関連文書・Git/GitHubの状態を確認し、必要なテンプレートと接続を揃える | 対象が不明な場合のリポジトリ、導入元、公開範囲や不足する権限 |
| Issueの準備 | 既存Issue/PR/着手記録を確認し、必要なIssueを発行。担当・ready-for-ai・必要な承認を確認する | 目的・範囲・担当が決められない点、既存作業との調整 |
| 全体像の整理 | 新規なら要件と構成を整理。既存なら現在の実装・設定・テスト・運用を調査する | 作りたいもの、制約、調査で不明だった前提 |
| 文書の準備 | system-context.mdとarchitecture.mdを必要に応じて作成・更新し、変更案を提示する | 全体要件、採用する構成、既存の規約・構成との差分 |
| 次の開発の準備 | 機能や優先順位を整理し、後続Issueの作成・分割と次の作業を提案する | 優先順位、設計・実装へ進むために必要な承認 |

Issueを発行したことと、その設計・実装が承認されたことは分けて扱います。AIは不足する情報だけを確認し、必要な承認を得てから対応する作業へ進みます。

### システムコンテキストとアーキテクチャ

人間が作成タイミングを指定する必要はありません。AIが個別機能の実装に入る前に、既存文書の有無と内容を確認して用意します。

| 文書 | 書く内容 | 人間が確認すること |
| :--- | :--- | :--- |
| docs/system-context.md | 目的・対象ユーザー・全体要件・用語・機能一覧・共通の前提 | 作るものと優先順位が意図に合っているか |
| docs/architecture.md | 採用する技術・構成・選んだ理由・制約・既定構成との差分 | 採用する構成と、その理由・影響が妥当か |

既存プロジェクトでは、確認できた現状と変更提案を区別します。調査Issueでは機能実装・リファクタリング・依存更新・API/Infrastructure変更を行いません。
AIはコード構成、起動/ビルド/テスト/デプロイ、API・認証・データ・外部連携、設定や秘密情報の所在、既存文書と不足を調べ、文書更新案・後続Issueへまとめます。秘密の値は文書へ記録しません。

## 4. プロジェクト統制は必要になったら導入する

プロジェクト統制は、複数のIssueの順序、担当者、共有ファイルの競合を調整するための仕組みです。
**初回に人間が設計書を読んで設定ファイルを作る必要はありません。** AIが必要性を判断し、使う範囲と設定案を提案します。

| 状況 | 進め方 | 人間が行うこと |
| :--- | :--- | :--- |
| 個別Issueを順に進められる | 通常のIssue/PR運用で始める | 目的と必要な設計・PRを確認する |
| 複数Issueの順序や複数人・AIの担当調整が必要 | AIが計画・メンバー台帳・担当や引継ぎの運用を提案する | 採用範囲、調整担当者、担当領域と権限、運用方針を決める |
| 導入範囲を決めた | AIが設定案と確認手順を準備する | 設定PRをレビューし、実際の担当割当・競合調整を行う |

詳細な仕様は[プロジェクト統制の設計](project-orchestration-design.md)、人間の調整手順は[手動Coordinator運用](manual-coordinator.md)です。必要になったときにAIの提案から参照できます。
読み取り専用の検査ツールは計画や候補を返し、担当や着手を確定しません。GitHub Projects・常駐実行基盤は別途必要性を判断する任意拡張です。

## 5. 準備ができたら

AIが、準備した文書・Issue・設定、検証結果、残る確認事項、次の作業を報告します。
人間は目的と構成・導入差分を確認し、必要な承認を返します。その後は[運用マニュアル](operations-manual.md)のとおり「進めてください」で継続できます。
