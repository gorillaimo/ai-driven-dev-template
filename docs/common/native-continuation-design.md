# 自律実行の設定・停止・再開の設計

## 1. 対象と提供範囲

人間の継続依頼を受け、利用中のAI開発環境で、担当Issueから進められる作業を選び、検証とPR準備まで進める。Codex Cloud、ローカルのAI開発ツール等を対象にする。必要な開発環境と接続は、アプリ・採用した検査・利用サービスに合わせて確認する。

この文書は共通の具体設計である。残量取得・自動停止・並列実行を全環境で実装済みと示すものではない。人間の採否判断と実装・環境での検証を分け、未提供の能力は未評価として報告する。承認・試験・変更経緯はIssue/PRに置く。

AI開発サービスがAIの実行を管理する。テンプレートは作業契約・候補選択・検証・途中保存・報告の方法を定める。AI向けの入口は[継続依頼の手順](development-rules.md#continuation-procedure)、GitHubに残す人間向けの様式は[記録例](operations-reference.md#continuation-records)にまとめる。人間向けの既定値と変更方法は[運用マニュアル](operations-manual.md#autonomous-settings)を参照する。自然言語での確認と、未提供の常時監視・強制停止は区別する。

## 2. 開始時に確認する能力

AIは下表の対応状況と今回の上限をIssueの着手記録へ要約する。人間に毎回環境設定や長いプロンプトを要求しない。

| 能力 | 確認すること・不足時の扱い |
| :--- | :--- |
| GitHubと作業場所 | Issue/PRの全候補・担当・承認・着手記録・最新main、branch/commitを確認できるか。全量不明や他作業との重複は対象の着手を止める |
| 実装・検証 | 対象アプリの編集/test/buildと必要なセキュリティ検査の実行先。利用中の環境で不可能なら、承認済みCI等を使うか未実施として保留する |
| 利用枠 | 現在のaccount/workspaceに対応する枠と取得方法。非対応なら件数/時間方式、対応していた取得口の故障なら停止して再確認する |
| 時刻 | 現在時刻と開始・期限を確認できるか。不明/逆行時は新規作業を始めず保存・照合する。時間を推測して延長しない |
| 複数エージェント | 起動・担当場所・状態確認・停止の能力、分割の人間承認。足りなければ順次進め、確認不能な稼働作業を置いたまま別方式で再実行しない |
| 独立レビュー | 実装とは別の実行コンテキストを使えるか。必須の場合、非対応を自己確認で代用せず、レビュー待ちとして報告する |
| 保存・報告 | commit/push、Issue記録、draft/通常PRの作成・読戻し。保存不能や応答不明を成功扱いせず、最後に確認できた状態を残す |

会話型の環境でも、GitHub接続と編集・テスト・PR作成の能力と、契約の利用枠を取得する能力は別に確認する。残量取得toolがないことを、同じサービスの全環境が非対応である根拠にしない。環境・接続が変わるたびに再確認する。

公式Codex App Serverには`account/rateLimits/read`と`account/rateLimits/updated`があり、`usedPercent`、時間窓、リセット時刻などを扱う。ただし、App Serverの機能をこの会話で呼べるとは推測しない。連携実装は任意で、既存の正規接続と許可を確認して採用する。tokenファイルの流用、非公開API、画面からの無断取得を前提にしない。

## 3. 候補選択とIssueごとの作業

1. 人間の具体指示を優先し、対象repository・人間owner・許可工程を確定する。「進めてください」は未提示の設計や新権限の承認にはしない。
2. 担当、ready-for-ai、当該工程の承認、依存、既存branch/PR・着手記録、変更領域を全候補で確認する。担当/承認が不足するIssueは、許可された準備まで進める。
3. 承認済みpriority、依存順、実Issue番号の順に候補を整理する。進行中のIssueの再開を先に照合し、局所的な確認待ちは当該Issueと下流へ限定する。全体不明や競合範囲不明なら新規着手を止める。
4. 第4章の停止条件を確認し、Issueごとのbranchと作業場所、目的・設計・検査・保存点を記録する。着手直前にも最新状態を読み直す。GitHubの着手記録を原子的なロックとは扱わない。
5. 要件・具体設計の確認後、受け入れ条件のテストを先に作り、実装・必要な検査・独立レビュー・指摘修正を行う。調査/設計だけの契約はその成果物までで止める。
6. PR準備完了・判断待ち・各工程の区切りで保存し、候補と利用枠を再確認する。下流に必要なマージは人間の判断を待つ。PR作成だけで依存完了やclaim解除にしない。
7. 対象なし、上限、停止、保存不能、承認/権限の喪失なら、第6章の保存と報告へ進む。状況確認だけの依頼では、許可済み作業を停止しない。

既存のIssue/branch/PRと担当調整の記録を使う。GitHubの記録だけで同時着手を原子的に防げるとは扱わない。他の人・AIとの同時着手があり得る場合は担当を調整し、確認できるまで対象を止める。

## 4. 利用枠と作業量の停止条件

### 4.1 初期設定と確認点

次はこの設計の初期設定値である。実装・採用時には対象Issue/実行記録へ実際の設定を記載する。値を変える場合は人間の判断を記録し、実行途中にAIが上限を増やさない。

プロジェクトの既定値は[.ai-workflow/autonomy.yaml](../../.ai-workflow/autonomy.yaml)、形式は[autonomy/v1 settings schema](../../.ai-workflow/schemas/autonomy/v1/settings.schema.json)で定義する。既存のIssue/Project等のv1とは独立した契約で、設定を置いたことは実行権限や自動停止の有効化を意味しない。項目ごとの範囲に加え、残量の大小関係と並列数を[静的検査](workflow-tools-guide.md#autonomy-settings)で確認する。

| 項目 | 設定値 |
| :--- | :--- |
| 1回の継続作業（run）の総Issue数 | 最大2件。工程へ着手した異なるIssueを数え、保留/失敗も除外しない。候補一覧の読取りだけは数えない |
| 同時開発 | 既定1件。独立性・環境能力・分割承認が揃う場合のみ最大2件。レビュー用を含め同時エージェント最大3 |
| 作業期限 | 開始から60分。50分以降は新規Issue/エージェント/修正巡回を始めず、最後の10分を保存・照合・報告に充てる |
| 修正→再検証・再レビュー | Issueごと最大2巡。進展なし・判断待ちではそれ以前でも保留する |
| 残量による新規着手停止 | 関連する枠のいずれかが残量30%以下 |
| 残量による保存優先 | 関連する枠のいずれかが残量15%以下、制限警告、または枠の枯渇 |
| 残量観測の鮮度 | 操作前60秒以内、かつ正しい対象と時間窓の観測。開始・子agent起動・工程境界・PR準備後に再確認 |

件数/時間/反復の上限は、残量が取得できる場合も適用する。並列作業の時間とIssue数は親run全体で数え、子agentごとに枠を増やさない。別agentの利用量を含まない観測は全体の十分な残量の証明にしない。

明示停止・権限/承認喪失を先に確認する。複数条件が当たる場合は、保存優先を新規停止より優先し、停止理由をすべて残す。1つの十分な値で別の不足・不明を打ち消さない。

60分はAIが工程境界で確認する期限であり、すべての環境で60分ちょうどに強制停止できる保証ではない。長時間commandは利用環境のtimeout/中断機能を確認し、残り時間に収まらないものを新しく始めない。機械的な監視・強制停止がない場合は、その制限を開始記録へ書く。保存用10分もサービスから追加の利用枠を得るものではない。

#### 設定変更の入口と適用範囲

通常の入口はAIへの自然言語の依頼とする。毎回の設定指定やファイル手編集を必須にしない。AIは現在の値と変更案、適用範囲・影響を確認し、明確な変更指示を不要に再承認させない。範囲が不明なら、今回だけか今後の既定値かを確認し、永続設定へ推測で反映しない。

設定は「初期値」「承認済みプロジェクトの既定値」「今回の明示指定」を分け、今回の明示指定を優先する。ただし、環境能力、契約/権限、人間の承認条件、必須検査、実装時に定める安全な範囲は上書きしない。不正・矛盾する設定は自動補正して実行せず、理由と修正案を提示する。

今回だけの指定はrunの作業記録へ実効値とともに残し、プロジェクトの既定値を変更しない。既定値の変更はGitで管理するプロジェクト設定の差分をAIが準備し、通常のPRで人間が確認する。既定値の変更は次のrunから適用し、進行中のrunへ黙って遡及しない。明示的に今回のrunも変更する指示がある場合は、残量・累積値・作業状況を再確認して記録し、経過時間や修正巡回をリセットしない。

作業期限を変更する場合は、最後の10分を保存・照合・報告に充てる新規停止時刻も連動させる。例えば90分なら80分以降に新規着手を止める。保存用の余裕を確保できない値は、そのまま採用せず修正案を提示する。

設定確認の依頼には、既定値・今回だけの指定・実効値・残量取得の対応状況を分けて答える。設定ファイルの形式と静的検査は提供し、手編集の方法はtool guideへ記載する。AIは設定の参照commit・revisionと検査結果を記録し、欠落・不正・適合未確認なら設定の確認・修正提案までとし、複数Issueの継続を開始しない。初期値で黙って補わない。今回だけの明示指定は項目の範囲と大小関係をAIが照合し、出所と実効値を記録する。今回指定の解析・設定合成・run累積/停止の機械的な制御は未実装であり、保存ファイルの適合を合成後の機械検証や利用枠取得・停止の証拠にしない。

### 4.2 残量を取得できる場合

信頼できる正規の観測について、対象account/workspace、limit/bucket、各window、観測時刻、used/remainingの意味、リセット時刻の有無を確認する。`usedPercent`なら`100-usedPercent`を残量にする。関連する複数window/bucketをすべて評価し、最も少ない残量を使う。window名を5時間/週へ固定しない。

有限の0〜100の数値だけを受理し、欠落・NaN・範囲外・対象不一致・未来時刻・60秒超の観測は不明とする。必要な枠が欠けていれば、他の枠だけを見て継続しない。contextの残量、今回のtoken数、APIの毎分上限、プラン名から契約枠を推測しない。人間からの一度だけの申告は開始判断の参考で、継続監視の代替にはしない。

| 観測/条件 | 判断 |
| :--- | :--- |
| すべての関連枠が30%より多い | 他の着手条件・件数/時間上限も満たす場合だけ開始できる |
| 15%より多く30%以下 | 新規Issue/子agentを始めない。進行中のIssueは、検証・記録・PR準備まで十分な余裕が見込める場合だけ区切りまで進める。見込めない場合は途中保存する |
| 15%以下、警告、枯渇 | Issue完了を強行しない。新しい開発・レビュー・修正巡回を止め、稼働処理の状態確認・保存・報告を優先する |
| 観測不明・取得故障 | 新規着手を止め、進行中は安全な保存点へ進めて再確認する。自動retryは1回まで。回復しなければ停止し、無制限に待たない |

新規停止と保存停止を区別する。30%以下でも現在のIssueの完了を保証せず、15%以下なら未完了のまま保存できる。複数agentの消費、他session、表示遅延や追加修正により途中で枯渇する可能性は残る。

必要な独立レビューに新しいagentが必要でも、新規停止中には起動しない。レビュー未実施として保存し、必須条件を省いて完成させない。CI待ちもrunの経過時間に含め、期限時に結果未確認ならその状態を報告する。既に起動したCIを一律にcancelする指示や、結果を待つための無期限延長にはしない。

### 4.3 最初から残量取得が非対応の場合

件数/時間/反復で区切る方式を開始時に明記する。初期設定は最大2 Issue/60分/修正2巡、順次実行とし、残量は「不明」のまま残す。非対応だけを理由に通常の会話開発を禁止しない。

対応していた取得口の故障・古い観測・不正値を「非対応」へ読み替えて自動継続しない。方式変更が必要なら状況と代替上限を人間へ報告して判断を受ける。時刻も確認できない場合は時間方式を成立させず、新規開始を止めて保存する。

追加購入、有料resetの消費、モデル変更、別accountへの切替、上限の引上げは自動実行しない。通常のコンパクションも契約枠が回復した根拠にはしない。

## 5. 並列作業と横断検証

並列化は任意であり、Codex Cloud等の名称だけで対応済みと判断しない。分割案にはprimary/統合担当、各Issueのbranch/作業場所・変更可能ファイル、共有領域、検証・停止方法を示し、既存規約どおり人間の承認を得る。停止・状態照合ができない子agentを自動起動しない。

共通API、schema、lockfile、認証、Infrastructure、依存するデータの変更は保守的に直列化する。ファイルが別でも意味上の依存を確認し、独立性が不明なら順次にする。worktreeはGit作業の分離であり、権限や通信の隔離を保証しない。サービス側の境界を確認し、必要な検査が安全に実行できなければ保留する。

各PRの単独検証に加え、同時に進めた変更の組合せについて、最新mainとPR headを固定し、適用/merge競合、共有契約、必要なtest/buildを確認する。利用中の作業場所や元branchを壊さず、一時作業場所または承認済みCIを使う。任意のP6部品を使う場合は、そのDocker等の採用条件を維持する。通常経路でP6の隔離実行や署名権限があると偽らない。

競合は元Issueのbranchへ戻して修正し、新headと組合せを再検証する。head/main更新で古い組合せ結果は失効する。横断検査を実行できなければ未実施と報告し、要件上必須ならレビュー可能な完成PRへ昇格しない。自己確認は独立レビューの代替にせず、必須レビュー未実施はdraft/待機にする。

## 6. 途中保存・停止・再開

### 6.1 保存点と記録

設計確定、先行テスト、実装の区切り、検証/レビュー、PR準備、停止判断時に保存する。小さな修正ごとに全検査を繰返す指示ではなく、[検査時点の規約](operations-reference.md#security-review-timing)と既存CIを維持する。

人間が確認する入口はGitHub Issue/PR。AIは[記録例](operations-reference.md#continuation-records)を使い、複数Issueを含むrunでは開始記録の正本URLを1つ決めて各Issueから参照する。各工程の記録を追記し、元の出所と累積を維持する。既存のIssue別plan/stateを採用済みなら併記し、未採用なら新しい共有台帳を必須にしない。共通設計へ作業経緯を追記しない。記録には次を含める。

- run識別子、人間owner、開始/保存時刻・新規開始停止時刻・期限、対象Issueと許可工程、利用枠取得の対応/不明・停止理由。
- 設定の参照commit・revisionと検査結果、今回だけの指定、その出所と実効値。
- 総着手Issue、稼働agent/未確認作業、Issueごとの修正巡回、実際の件数/時間/並列上限と終了用余裕。
- 各Issueのbranch、最後に確認したcommit/remote head・PR URL、未commit/未pushの有無と保護した保存先。
- 実施した検査/独立レビュー/統合の対象head・結果・参照。未実施・失敗・未評価を分ける。
- 未解決事項、次の具体操作、再開時に読み戻す対象、人間の判断事項。

GitHubへsecret、環境値、ソース/差分の原文、モデル入出力、account/課金情報の生データを転載しない。必要な割合/不明と停止理由だけを公開し、詳細は承認済み保存先へ置く。未完了でも安全な途中commit/pushは可能で、draft PRの作成は完成やIssue closeを意味しない。

### 6.2 保存故障と急な中断

push/PR作成・コメント投稿が応答不明なら、新しい操作を盲目的に繰返さずremote branch/PR/コメントを読み戻す。通信不能なら確認済みローカルcommit等を保持し、未公開/保存先未承認を明記する。保存不能を保存済みと書かず、後続Issueの開始を止める。

明示停止・承認撤回では新規変更・外部更新を止め、残る処理と保存の可否を確認する。保存/push等の外部操作まで停止指定の対象なら、勝手に続行しない。子agent/commandの停止を確認できない間は、対象を再割当しない。

サービスの急な制限到達、環境消失、強制終了では最終保存/投稿できる保証はない。保存点を増やして損失を抑えるが、未commit/未push作業の復元を保証しない。

### 6.3 再開と次のrun

再開時はGitHubの担当・契約/承認・main/PR head、最後の確認済みcommit、未公開差分、稼働作業・停止状態、利用枠・期限を照合する。不明を空状態に置換せず、重複実行・無断claim解放をしない。

単なる状況確認、コンパクション、会話/環境の再接続では同じrunの開始時刻・期限・総Issue・修正巡回をリセットしない。保存されたrunが期限内で進行中なら同じrunとして再開する。時刻不明や累積不明は再確認まで停止する。

終了/上限で停止した後、人間から新たな「進めてください」等の継続依頼があれば、現在の条件を確認し、同じ既定方針の新runとして開始できる。その旨と新しいrun識別子・期限を記録し、未完了Issueを最初に照合して今回の総Issue数へ含める。Issueごとの修正巡回や未解決指摘は引き継ぎ、人間の判断なしに0へ戻さない。利用枠不足・未確認の旧作業・承認不足を新runで迂回しない。AIが自動で新runを連結して上限を無効化することは禁止する。

終了報告は完了/PR、途中保存、未実施検査、停止理由、残作業・推奨マージ順をまとめる。朝や定刻まで待たず、毎Issueで人間の返答を要求することも前提にしない。マージ・deploy・Releaseは人間の判断を維持する。

## 7. 実装の分け方と検証

最初は本設計と共通案内をレビューする。設計の採用で、全環境の連携や機械的な制御が提供されたとは扱わない。後続は親[#52](https://github.com/gorillaimo/ai-driven-dev-template/issues/52)の実装契約を整理し、次の単位でテスト先行にする。

| 段階 | 変更候補・検証 |
| :--- | :--- |
| 保存する既定設定・静的検査 | `.ai-workflow/autonomy.yaml`と独立schema、既存workflow-schema入口での型/範囲/大小関係の検査を提供。自律起動や実行時停止は行わない |
| 通常の会話手順への接続 | AGENTSから開発規約の継続手順へ接続し、設定・候補・上限・保存/再開をAIが確認する。Issue/PR向け記録例を提供。代表Issueの確認結果と未実証シナリオはIssue/PRへ記録し、全環境での制御実証と扱わない |
| 任意の判断補助 | 既存`tools/workflow-continuation/controller.mjs`の`decideContinuationBudget({policy, observation, run, now})`が、注入した値から継続/新規停止/保存優先・操作別候補・局所保留・固定理由codeを返す。既存P7テスト入口で確認。[APIと範囲](../../tools/workflow-continuation/README.md#budget)を参照。実験用host/会話手順へ自動接続せず、残量/時計の取得・実停止/保存は行わない |
| 任意の環境接続 | 正規に公開された残量/agent/停止/保存能力を接続する。現在の会話で残量取得不可なら非対応を維持。新環境・認証・課金・定期起動を暗黙に追加しない |

新しいJS/Python sourceは現行246件と固定argv10の上限を確認してから計画する。検査対象除外や上限緩和で追加余地を作らない。既存schemaの受理範囲・実行権限・起動制限・台帳の意味を変更しない。機械補助の形式/版が必要なら別契約として承認し、Issue v1の完了や権限を推測で埋めない。

### 設計のシナリオ確認と先行試験の期待

以下は机上確認と後続実装の期待結果であり、実モデル/全環境での実証済みテストではない。

| ID | 条件 | 期待結果 |
| :--- | :--- | :--- |
| N01 | 残量31%、全条件正常 | 件数/時間内なら次Issueを開始可能 |
| N02 | 残量30%ちょうど | 新規Issue/子agentは開始しない。進行中も余裕がなければ保存 |
| N03 | 残量15%ちょうど、または0%/警告 | 保存優先。完成・最終投稿を保証せず、未完了を保持 |
| N04 | 片方のwindowは80%、他方は20% | 少ない残量を使い新規停止。usedPercent=80なら残量20% |
| N05 | NaN/範囲外・対象不一致・未来・61秒前・必要枠欠落 | 不明として新規停止。60秒ちょうどは鮮度内。数値を丸めたり別枠で補完したりしない |
| N06 | 最初から残量取得が非対応 | 残量不明を記録し、最大2 Issue/60分等で順次進行 |
| N07 | 対応していた残量取得が故障 | 1回まで再確認、回復しなければ保存停止。非対応へ自動変更しない |
| N08 | 総着手2件、または経過50/60分 | 3件目は開始しない。50分で新規Issue/agent/修正巡回を止め、60分で保存/照合結果を報告。強制終了能力の有無を区別 |
| N09 | 修正2巡完了/進展なし、1件だけ承認待ち | 当該Issueを保留。全体上限と独立性が許す別候補だけ継続 |
| N10 | 共有path/意味上の依存、または未マージ依存 | 直列化/下流保留。branchが別でも独立と扱わない |
| N11 | 並列機能なし・分割承認なし | 順次。独立レビュー必須で別context不可ならレビュー待ち |
| N12 | 保存前強制停止/未push/投稿応答不明 | 最後の確認済み地点から照合し、保存済み/完了を捏造しない |
| N13 | 同runへの再接続/状況質問/別session | 上限と履歴を引継ぎ、重複起動せず時刻/利用枠を再確認 |
| N14 | 終了後の人間の新たな継続依頼 | 新runを記録し再確認。未完了Issue・指摘・修正巡回は引継ぎ、不足枠を迂回しない |
| N15 | 別agentが消費、head/main更新、検査未実施 | 枠を再確認、古い検証を失効し、検査省略で完成させない |

後続の判断補助ではN01〜N15の数値/状態境界をfake入力と時計で先に失敗させ、非実行・非変更も検査する。自然言語手順の確認、純粋関数の合成試験、実際の会話開発・並列/停止の立会い確認は別の証拠としてIssue/PRへ記録する。割合停止でサービス制限を回避したことや、全作業の完了を保証しない。
