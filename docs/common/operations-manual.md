# v2 運用マニュアル

**具体的な作業を指示することも、次に行う作業の判断をAIに任せることもできます。**
AIに任せたいときは「進めてください」と依頼できます。AIがIssue・コード・作業記録を調べて進捗を把握し、次に行う作業を選びます。人間は目的を決め、AIからの確認事項に答え、成果物をレビューします。
工程ごとの長いプロンプトや検査コマンドを覚える必要はありません。

## 1. 初回はセットアップから始める

**最初にAIへ送るプロンプトは、[初期セットアップ](operations-setup.md)に掲載しています。**

| 始めたいこと | 最初に使う依頼例 |
| :--- | :--- |
| 新規プロジェクトを始める | [新しいプロジェクト](operations-setup.md#new-project) |
| 既存プロジェクトへ初めて導入する | [既存プロジェクトへの導入](operations-setup.md#existing-project) |

初回のセットアップでは、プロジェクト全体で作りたいもの・目的・制約を伝えます。AIが必要なIssueの準備と全体要件・構成の整理を進めます。
準備中も、希望する作業や変更点を具体的に指示できます。AIから質問や承認の依頼があれば、その内容を確認して回答します。
セットアップ後はこのマニュアルを使います。初回用プロンプトを送り直す必要はありません。
現在はv2開発版です。採用する範囲や移行時の確認は[試用前の確認表](v2-adoption-checklist.md)にまとめています。

開発中のプロジェクトを新しい会話や別のAIへ引き継ぐ場合は、対象リポジトリ・目的・人間の担当者を伝え、「作業記録を確認して開発を引き継いでください」と依頼します。対応するIssueが決まっていれば、その番号も渡します。

## 2. Issueへの着手と作業の継続を依頼する

各Issueへの着手時には、AIがIssue本文から、そのIssueで達成したいことと作業範囲を確認します。本文に記載されていれば、対象Issueの番号を伝えるだけで依頼でき、毎回説明し直す必要はありません。
対象Issueが決まっていない場合も、AIに次の作業の選択を任せられます。AIは既存の担当・着手記録・承認状況を調べ、確認や調整が必要なら提案します。

| 場面 | 人間が伝えること | AIが行うこと |
| :--- | :--- | :--- |
| 対象Issueを指定したい | 「Issue #123に着手してください」 | Issue本文の目的・範囲と着手条件を確認する |
| 今回行う作業を具体的に指示したい | 「今回は設計だけ進めてください」 | 指定された範囲で進め、実装には入らない |
| 次に行う作業や進め方をAIに任せたい | 「進めてください」 | 進捗・残っている作業・承認状況から次の作業を選び、許可された範囲で進める |
| 提示された設計でよい | 「その設計で進めてください」 | 承認された範囲でテスト・実装・検証を進める |
| 方針を変えたい | 「○○に変更してください」 | 影響を確認し、Issue・計画・必要な文書を更新する |
| PRをマージした | 「マージしました。進めてください」 | マージ結果と最新mainを確認し、次の作業を整理する |
| 中断・再開したい | 「ここで中断してください」／「作業を再開してください」 | 作業記録を残す／記録と実際の状態を照合して再開する |

具体的な指示があれば、AIはその意図とIssueの範囲に合わせて進め方を調整します。次の作業をAIに任せることもできるため、人間が工程を毎回指定する必要はありません。
作業が止まる場合、AIは理由・必要な判断・次の一手を短く示します。

## 3. AIに任せること

- 最新の規約・Issue・PR・着手記録を読み、作業の重複や競合を確認する。
- 目的に沿って次の作業を選び、必要ならIssueの作成・整理、分割、担当や着手条件の確認を行う。
- 変更の大きさとリスクから、必要な調査・設計・検査と、人間へ確認する時点を判断する。
- 作業ブランチを用意し、要件・設計・必要なAPI定義を整え、テスト先行で実装・検証する。
- 変更対象に合うアプリのテスト・セキュリティ検査を選び、合意した範囲・タイミングで実行する。
- 要件・差分・実際の検証結果をAIがレビューする。独立AIレビューが必要な作業では、実装とは別の実行コンテキストを使い、自己確認で代用しない。
- 検査やレビューの指摘を確認し、承認済みの範囲で修正・再検証する。仕様変更や上限到達、判断できない指摘は人間へ戻す。
- 変更内容、検証結果、未確認事項を記録し、レビューできるPRを用意する。

AIは[AGENTS.md](../../AGENTS.md)と[開発規約](development-rules.md)に従います。
担当者・`ready-for-ai`・承認が不足する場合は着手条件を整え、他の人やAIの作業がある場合は調整を求めます。
目的が曖昧なときや、次に進める作業が決められないときは、候補と確認点を提示します。

### 検査・レビューを行うタイミング

AIは着手時に、変更内容とリスクから「何を、いつ確認するか」を整理します。修正中は影響するテスト・検査と該当指摘の再確認を行い、PR前には必要な検証・レビューが揃っているかを確認します。会話の指示が来るたびに、全検査を一律にやり直す前提ではありません。

例えば、説明文だけの訂正を理由に、毎回コンテナイメージを全面検査して無関係な脆弱性まで修正する作業を追加しません。依存・実行基盤・イメージの変更、検査結果の期限切れ、新たな重大問題、公開前の確認などは再検査が必要です。採用済みの必須検査は維持します。

現在のテンプレートCIはPRへのpushごとに起動します。変更のない検査結果を自動再利用する機能は未実装なので、工程を整理しただけでCIの重複実行まで省略されるわけではありません。詳しい[検査時点と再確認の例](operations-reference.md#security-review-timing)を参照してください。

実行できない検査・独立AIレビューは未実施として報告します。別AIの自動起動や実モデルによる継続運用の提供状況は、[追加部品の採用条件](v2-adoption-checklist.md#optional-components)を確認します。

### 自律実行の既定値と設定

プロジェクトの既定値は[設定ファイル](../../.ai-workflow/autonomy.yaml)で管理し、値を検査できます。次の表はテンプレートの初期値です。変更後は設定ファイルの値を確認します。設定の自動適用・残量取得・自動停止は、まだ未実装です。

| 項目 | 初期値 |
| :--- | :--- |
| 1回に進めるIssue数 | 最大2件 |
| 作業時間 | 最大60分。最後の10分は保存・報告に充てる |
| 同時に進めるIssue数 | 1件 |
| 修正・再検証の繰返し | Issueごとに最大2巡 |
| 新しいIssueへの着手を止める残量 | 30%以下 |
| 作業途中でも保存を優先する残量 | 15%以下 |

残量を取得できない環境では、件数・時間で区切ります。設定を変えたいときはAIへ依頼します。

| 変えたいこと | 依頼例 |
| :--- | :--- |
| 今回だけ変える | 「今回は1 Issue、最大30分で進めてください」 |
| 今後も使う既定値を変える | 「このプロジェクトでは、今後の作業時間を最大90分にしてください」 |
| 現在の設定を確認する | 「現在の設定と、今回だけ変更している項目を教えてください」 |

今回だけの指定は作業記録に残し、設定ファイルを変えません。今後も使う既定値の変更は、AIが設定ファイルの差分を用意し、値の検査後にPRで確認します。必要な検査や承認は設定変更後も維持します。[手編集・検査の手順](workflow-tools-guide.md#autonomy-settings)も参照できます。

AIは工程の区切りで変更・検証結果・残作業を保存します。中断後は「進めてください」と依頼すると、記録と現在の状態を確認して再開します。突然の制限到達では最終保存できない場合があります。詳しい[設定・停止・再開の設計](native-continuation-design.md)を参照してください。

## 4. 人間が判断すること

**作るもの・優先順位・提案の妥当性・成果物を確認します。**
AIは、設計の承認、未決の仕様、権限や担当の調整、共通構成の変更について、判断に必要な情報と選択肢を添えて提示します。
承認するときは、何に同意するか分かる返答にします。単なる継続依頼を、まだ提示していない設計や次のIssueへの承認に読み替えません。

複数人・複数AIでの担当割当や引継ぎが必要になったら、AIが[担当調整の手順](manual-coordinator.md)から参照すべき箇所を選び、推奨案と人間が判断すべき点を示します。まずはIssueを1件ずつ進める運用から始められます。
マージ・本番反映・Releaseは、それぞれの対象と影響を確認して判断します。

## 5. PRを確認する

**「依頼したことが実現しているか」「確認できた範囲と残る問題を受け入れられるか」を判断します。**
まずPRの説明と対応Issueを読み、記載された成果物・検証結果を確認します。詳細なYAMLやログは、根拠を確かめたいときに参照します。

### PR本文の項目ごとの読み方

[PRテンプレート](../../.github/pull_request_template.md)を基本に、次を確認します。見出しがまとめられたり順序が変わったりするPRでも、同じ内容を確認します。

| PR本文の項目 | 書かれていること | どこを、どう確認するか |
| :--- | :--- | :--- |
| 対応issue | このPRで対応する作業へのリンク | Issueを開き、目的・作業範囲・完了条件が今回のPRと一致するか。`Closes #123`は既定ブランチへのマージ時にIssueを閉じる指定なので、閉じてよい範囲か |
| 受け入れ条件ごとの対応 | 各完了条件に対して、何を実装・確認したか | 条件ごとに、画面・文書・テスト結果などの根拠を開く。チェック済みでも未実施や未検証が残っていないか。チェックはAIの報告であり、人間の承認とは別 |
| 更新したドキュメント | 要件・設計・API仕様・利用手順などの更新先 | リンク先や差分を読み、今回合意した仕様・使い方と一致するか。関係する文書の更新漏れがないか |
| 変更概要 | 何を、なぜ変え、どう使えるようになるか | 依頼した目的に合うか。画面や文書は実物でも確かめ、期待した変更前後になっているか |
| 影響範囲 | 画面、処理、構成、権限、データなどへの影響 | `Files changed`（変更ファイル）と説明を見比べ、無関係な変更や、説明されていない影響がないか |
| 変更リスク | Low / Medium / Highの分類と理由 | 影響の大きさに合う分類か。必要な事前承認がIssue等に記録されているか。不明なら分類理由の説明を求める |
| Quality Gates | 性能等（NFR）・安全性（Security）・障害からの復旧（Resiliency）の確認 | 該当する観点の結果・根拠・未確認事項を読む。「該当なし」の理由は妥当か。「未確認あり」が今回の目的や利用に影響しないか |
| 実行した検証 | 実行したテスト、結果、対象、未実行の検査 | 条件に合うテストや実物確認があるか。`Checks`のCI結果も開き、最新の修正に対して成功しているか。模擬試験・0件・未実行を実環境の成功と混同しない |
| プロトタイプ由来の確認結果 | 試作品で分かったこと、本実装へ反映・流用した範囲 | 試作品の制約が要件・設計や実装へ反映され、流用部分が本実装として再検証されているか。試作品を使っていなければ該当なし |
| 残課題・別issue候補 | 未対応・未検証・既知の制約と、後で扱う作業 | 今回の完了条件に必要な作業を先送りしていないか。後続Issue・対応方針があり、残した状態で今回の変更を受け入れられるか |

### 確認後の判断

内容が意図どおりで、必要な検証と承認が揃い、残る制約を理解できたら承認・マージを判断します。CI成功だけで仕様の正しさまで保証されるわけではありません。
不足・失敗・分からない点があれば、PRコメントやAIとの会話で説明・修正を依頼します。例：「受け入れ条件2が満たされた根拠と、未検証の範囲を説明してください」。確認できるまでマージを保留します。
用語やCI結果の読み方、修正依頼の例は[レビューの参考資料](operations-reference.md#人間側のレビュー観点)を参照してください。

## 6. 止まったとき・引き継ぐとき

「何が止まっているか、次に何を判断すればよいか教えてください」と依頼します。
AIは元の記録を保ち、Issue・担当・ブランチ・PR・承認・未反映の作業を照合します。
記録が不足・破損している場合は、確認できたところから手動で現在地を整理し、必要な承認を取り直します。

人間がファイルを修正した場合や、別の人・AIへ引き継いだ場合は、その事実を伝えてください。
具体的な対処例は[トラブルシューティング](operations-reference.md#トラブルシューティング)、移行前の運用へ戻す方法は[移行ガイド](migration-v1-to-v2.md)にあります。

規約はAIが読む自然言語の指示です。検査ツールはNode.jsで実行し、計画や記録の矛盾を調べます。AIはその結果を使って作業を進めます。
Node.jsは開発管理用なので、開発するシステムの言語は問いません。テンプレート運用の検査と、作るアプリ自身のテストは別に行います。
Project用の台帳や高度な調整は、必要な範囲で追加できます。
