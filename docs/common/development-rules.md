# プロジェクト開発規約・プロセス

このドキュメントは、AIに読ませるための開発規約である。AIは、ここに書かれたルールを本プロジェクトの最上位の行動規範として扱うこと。

本プロジェクトでは、**issueを開発の最小単位**とする。AIはissue本文、関連ドキュメント、受け入れ条件を根拠として作業し、issue外の変更を勝手に実装してはならない。

## 1. デフォルト技術スタック

以下は、特に理由がない場合に採用するデフォルト構成である。AIはデフォルト構成を勝手に変更してはならない。

- **Frontend**: Flutter (Mobile/Web) または Next.js (TypeScript)
- **Backend**: Hono (TypeScript)
- **Infrastructure**: AWS (AWS CDK v2 / TypeScript)
- **Runtime**: AWS Lambda + AWS Lambda Web Adapter
- **Auth/Hosting**: AWS Amplify (Auth / Hosting)

要件、制約、運用条件、チーム体制、既存資産、コスト、セキュリティ、拡張性などの理由でデフォルト構成が適さない場合は、実装前に `docs/architecture.md` を作成または更新すること。未規定のクラウドサービス、実行基盤、認証基盤、データストア、外部サービス、主要フレームワークを採用する場合も同様とする。

`docs/architecture.md` には、採用アーキテクチャ、デフォルト構成との差分、採用理由、却下した選択肢、影響範囲、未決事項を記録し、人間の明示的な承認を得るまで実装してはならない。

### 1.1 メッセージ管理 / 多言語対応準備

AIは、多言語対応を今すぐ実装する場合も、実装しない場合も、ユーザーに表示する文言をコードへ直接散在させてはならない。画面表示、ボタン、ラベル、ヘルプ、バリデーション、エラー、通知、メール文面などのユーザー向けメッセージは、メッセージ定義ファイルまたはメッセージ管理モジュールに集約すること。

Frontendでは、Next.jsの場合は `messages/`、`i18n/`、`locales/` などの専用領域、Flutterの場合は `l10n/` や ARB へ移行しやすい構成を使うこと。最初は単一言語のみでもよいが、キー名は後から言語を追加できる粒度で定義すること。

Backendでは、APIレスポンスとしてユーザー表示用の文章に依存しないこと。可能な限り安定した `errorCode`、`code`、`reason` などの機械可読なコードを返し、表示文言はFrontend側のメッセージ定義で解決する。Backendがメールや通知などユーザーへ直接文面を送る場合も、文言を専用ファイルへ集約すること。

AIは、既存のメッセージ管理方針がある場合はそれに従う。方針が未定の場合は、実装前にメッセージ定義ファイルの配置、キー命名、対象言語、Fallback方針を確認事項として提示すること。

## 2. ディレクトリ構成

モノレポ構成を採用し、AIは常にフルパスを意識してコードを生成すること。

- `docs/system-context.md`: [重要] アプリ全体のビジョン、全体要件、機能単位一覧、用語集、共通ルール
- `docs/architecture.md`: [重要] 採用アーキテクチャ、技術スタック、デフォルト構成との差分、設計判断
- `docs/prototype.md`: 営業デモ、要件確認、画面遷移確認、技術検証のためのプロトタイプ範囲と結果
- `docs/requirements/`: issueまたは機能別の要件定義書
- `docs/design/`: issueまたは機能別の設計書、シーケンス図 (Mermaid)
- `docs/api/`: API仕様書 (`openapi.yaml`)
- `docs/common/`: 開発規約、運用マニュアル、テンプレート
- `packages/frontend-next/`: Next.js プロジェクト
- `packages/frontend-flutter/`: Flutter プロジェクト
- `packages/backend/`: Hono プロジェクト
- `packages/infra/`: AWS CDK プロジェクト

issueに紐づくドキュメントを新規作成する場合は、原則として `[issue-number]-[feature].md` の命名を使うこと。例: `docs/requirements/123-user-login.md`

## 3. issueベース開発の原則

AIは作業開始時に、必ずissueを作業契約として確認すること。

### 3.1 issueから読み取る情報

- 目的
- 背景
- スコープ
- 非スコープ
- 受け入れ条件
- 影響範囲
- 関連ドキュメント
- テスト観点
- 未決事項

### 3.2 作業開始時の義務

AIは実装前に、以下をユーザーへ報告すること。

- issueの目的の要約
- 受け入れ条件の要約
- 変更が必要なファイルまたは領域
- 参照したドキュメント
- 不明点
- 実装前に更新すべきドキュメント

不明点がある場合、AIは推測で実装してはならない。質問、またはissue本文・ドキュメントの更新提案を行うこと。

### 3.3 issue外作業の禁止

AIは、issueの受け入れ条件に直接関係しない改善、リファクタリング、仕様追加を勝手に行ってはならない。必要性を見つけた場合は、別issue候補として提案すること。

### 3.4 マルチエージェント作業の原則

マルチエージェント作業は、Codex、Claude Code、その他のAI開発ツールを含む一般ルールとして扱う。AIは特定ツールの機能差に依存せず、issue本文、関連ドキュメント、受け入れ条件を作業契約として扱うこと。

`ready-for-ai` ラベルは、AIに依頼できる状態を示す。自動着手、担当確定、排他制御を意味しない。

担当（assignee）は、issueの責任を持つ人間のGitHubアカウントとして扱うこと。AIエージェント名やツール名ではない。AIは、担当（assignee）に設定された人間、またはその人間から依頼された作業としてissueに着手すること。

AIは、担当（assignee）が未設定のissueに着手してはならない。着手前に、issueの担当、着手コメント、既存PR、他エージェントの作業有無を確認すること。

AIはissue確認時に、マルチエージェント化が有効かを判断すること。小さなドキュメント修正、単一ファイル変更、判断待ちが多いissueでは、原則として単一エージェントで進める。調査、設計、実装、検証を独立して進められる場合や、担当ファイルを明確に分離できる場合は、マルチエージェント化を提案してよい。

マルチエージェント化が有効だと判断した場合、AIは実行前に分割案を人間へ提示し、承認を得ること。人間が明示的にマルチエージェント利用を指示した場合を除き、AI判断だけで複数エージェント作業を開始してはならない。

分割案には以下を含めること。

- primary agent または統合担当者。
- 各エージェントの担当目的。
- 各エージェントが変更してよいファイルまたは領域。
- 各エージェントが触ってはいけない非担当領域。
- 統合時に確認する受け入れ条件と検証観点。
- 単一エージェントで進める場合と比べた利点とリスク。

複数エージェントで作業している場合でも、AIはissue外の改善、リファクタリング、仕様追加を勝手に行ってはならない。また、他エージェントや人間の変更を理由なく巻き戻してはならない。

## 4. 上流工程プロセス (Definition as Code)

AIは実装コードを書く前に、以下のステップを順守し、人間の承認を得る義務がある。

### STEP 0: アプリケーション全体定義 / アーキテクチャ設計

- 個別の機能実装前に必ず `docs/system-context.md` と `docs/architecture.md` を作成・参照すること。
- アプリの目的、共通ドメインモデル、用語定義、エラーハンドリング、セキュリティ、権限、運用前提を明文化する。
- 採用アーキテクチャ、技術スタック、クラウド、実行基盤、認証基盤、データストア、外部サービス、デフォルト構成との差分を明文化する。
- デフォルト構成から外れる場合は、理由、比較した選択肢、影響範囲、未決事項を `docs/architecture.md` に記録し、人間の承認を得る。
- 要件定義、設計、実装、テストを行うissueとして分割すべき機能単位一覧を明文化する。
- 全体定義またはアーキテクチャの変更は全機能に波及するため、人間の明示的な承認を必要とする。

### 任意 STEP 0.5: プロトタイプ作成 (Prototype Track)

- 営業デモ、要件確認、画面遷移確認、技術検証を目的とする場合、STEP 0 の後、通常の要件定義・設計・本実装に入る前にプロトタイプを作成してよい。
- プロトタイプは `docs/system-context.md` と `docs/architecture.md` を入力として作成し、目的、再現する範囲、再現しない範囲、本番アーキテクチャとの差分、検証結果、後続issue候補を `docs/prototype.md` に記録すること。
- プロトタイプは本番品質として扱ってはならない。本番DB、本番認証、本番決済、本番外部API、本番権限、監査ログを安易に接続してはならない。
- 画面遷移は、プロトタイプ前に主要フロー、画面一覧、入口、出口を仮決めし、プロトタイプ後に見直すこと。プロトタイプで確定した仕様は、必ず `docs/requirements/`、`docs/design/`、`docs/api/openapi.yaml`、`docs/architecture.md`、または後続issueへ反映すること。
- プロトタイプコードを本実装へ流用する場合は、テスト、セキュリティ、アーキテクチャ適合性、メッセージ管理、多言語対応準備、型安全性を再確認すること。流用判断は issue または PR に明記すること。

### STEP 1: 要件定義 (Requirements as Code)

- issueに基づき、`docs/requirements/[issue-number]-[feature].md` を作成または更新する。
- `docs/system-context.md` の全体ビジョン、`docs/architecture.md` の採用構成と矛盾がないか確認する。
- 要件定義書には、アプリ名、アプリ概要、対象プラットフォーム、対象ユーザー、利用シーン、スコープ、非スコープを明記する。
- 機能の入力、出力、正常系、異常系、権限、境界値を明文化する。
- データ要件、認証認可、ユーザー向けメッセージ管理、多言語対応方針、外部連携、非機能要件、未決事項を明記する。
- 受け入れ条件と要件の対応関係を明記する。
- 不明点は推測で補完せず、確認事項としてユーザーに提示する。
- テンプレート本体の改善issueでは、利用先プロジェクトに不要な履歴ドキュメントを残さないため、原則として `docs/requirements/` にissue別ドキュメントを作成しない。issue本文と既存共通ドキュメント更新で要件整理を代替する。

### STEP 2: 設計 (Design as Code)

- `docs/design/[issue-number]-[feature].md` にシステム構成、データフロー、責務分担を記述する。
- 複雑なロジック、外部連携、認証認可、非同期処理は Mermaid 記法で可視化する。
- Backend、Frontend、Infrastructure のどこに変更が必要かを明記する。
- テンプレート本体の改善issueでは、利用先プロジェクトに不要な履歴ドキュメントを残さないため、原則として `docs/design/` にissue別ドキュメントを作成しない。必要な設計判断はissue本文、PR本文、または更新対象の共通ドキュメントに残す。

### STEP 3: インターフェース定義 (Interface as Code)

- API変更がある場合、`docs/api/openapi.yaml` を更新する。
- IFは、エンドポイント、型、リクエスト、レスポンス、エラー形式、認証要件を含めること。
- API仕様は実装の契約であり、直感による実装で変更してはならない。
- 共通APIや共通モデルの変更は、実装前に人間の承認を得ること。

## 5. 実装・構築プロセス (EaC徹底ルール)

上流工程の承認後、以下のルールに従い実装を行う。

### 5.1 承認フロー

AIは実装前に、必ず以下を提示して人間の承認を得ること。

- 対応issue
- 実装方針
- 変更予定ファイル
- 追加・更新するテスト
- ドキュメント更新の有無
- Architecture / Infrastructure / API / 型定義への影響

### 5.2 Test-Driven Development (TDD)

- AIはロジックの実装を開始する前に、必ず受け入れ条件に対応するテストコードを先に提示、または作成しなければならない。
- テストは正常系だけでなく、異常系、権限、境界値、回帰観点を含めること。
- 実装コードは、提示したテストをすべてパスすることを最低条件とする。
- リファクタリングを行う際も、既存のテストがパスし続けていることを検証すること。

### 5.3 Infrastructure as Code

- Lambdaのハンドラ、権限、環境変数、外部リソースの追加は、必ず `packages/infra/` のCDKコードとセットで提案すること。
- 権限は最小権限を原則とする。
- 手動作成が必要なAWSリソースを前提にしてはならない。必要な場合は、理由と運用手順を明記すること。

### 5.4 Type Safety

- BackendとFrontend (Next.js) 間では、Honoの `hc` (RPC) 等を活用して型を共有すること。
- Flutterに対しては、OpenAPI定義から型安全なクライアントを生成する方針をとること。
- API変更時は、型生成または型共有の更新漏れがないか確認すること。

### 5.5 Lambda Web Adapter Compliance

- ステートレスな設計を厳守すること。
- 実行環境に依存する永続的な一時ファイル保存を行ってはならない。
- コールドスタート、環境変数、ログ出力、タイムアウトを意識すること。

## 6. プロンプト指示時の約束事

- **issue起点**: 指示を受けた際、AIはissue本文またはユーザーが提示したissue相当の情報を作業の起点にすること。
- **ドキュメント参照**: 関連する `@docs/` 下のファイルを再読解し、既存仕様との矛盾がないか検証報告すること。
- **不確実性の排除**: 仕様に曖昧さがある場合は、推測で実装せず必ずユーザーに質問すること。
- **最小差分**: issueの完了に必要な範囲だけを変更すること。
- **品質保証**: 機能実装と同時に、対応するテストコードを必ず生成すること。
- **検証報告**: 作業完了時には、実行したコマンド、結果、未検証事項を報告すること。

## 7. チーム開発・Git運用規約

- **Issue First**: コミット、ブランチ、PRは原則としてissueに紐づけること。
- **Branch / PR First**: AIは、通常開発では `main` へ直接 push してはならない。issue単位で作業ブランチを作成し、そのブランチへ push したうえでPRを作成すること。
- **Branch Before Work**: AIは、issue着手時に現在のブランチと作業ツリーを確認し、通常開発ではissue番号を含む作業ブランチを作成してから変更を開始すること。
- **Work-in-progress Push**: AIは、通常開発では作業の区切りごとに作業ブランチへ push してよい。ただし `main` へ直接 push してはならない。
- **Issue Progress Log**: AIは、作業ブランチへ push した場合、issueコメントまたは指定された作業記録に、pushしたコミット、変更概要、実行した検証、未解決事項、次の作業を記録すること。
- **Direct Push Exception**: `main` への直接 push は、ユーザーが明示的に依頼し、かつテンプレート初期整備、小さなドキュメント修正、緊急修正などレビュー不要と判断された場合に限る。
- **Main Protection**: `main` への反映は、原則としてPR mergeによって行う。GitHubのブランチ保護で direct push を禁止することを推奨する。
- **PR Scope**: PRは対応issueの完了成果物として扱い、要件定義、設計、API定義、テスト、実装のどこまでを完了させるかをissue本文とPR本文に明記すること。
- **PR Timing**: 作業途中の push はPR作成を意味しない。PRは、issue本文に定義された「PRで完了させる範囲」を満たした時点で作成すること。
- **GitHub Issue Form**: GitHub上で作成されたissueは、Issue Formの入力内容を正式な作業契約として扱うこと。
- **Ready Label**: `ready-for-ai` ラベルがないissueは、実装前に不足情報を確認すること。
- **担当（Assignee）必須**: 担当（assignee）が未設定のissueは、AIが着手してはならない。
- **Multi-Agent Coordination**: 複数エージェントで作業する場合は、primary agent または統合担当者、担当範囲、変更予定ファイルを作業開始前に明確にすること。
- **Branch Naming**: ブランチ名にはissue番号と要約を含めることを推奨する。例: `feature/123-user-login`
- **Atomic Commits**: AIによる変更は、ドキュメント更新、テスト追加、実装、インフラ変更を理解しやすい単位に分けることを推奨する。
- **Conflict Prevention**: `docs/api/openapi.yaml`、`docs/system-context.md`、`docs/architecture.md`、共通型、共通コンポーネントへの変更は、実装前にチームで共有し、必要なら先行してマージすること。
- **Environment Sync**: 作業開始時と `git pull` 後は、必ず最新のコードベースと関連ドキュメントを再スキャンすること。
- **PR Description**: PR本文には、対応issue、受け入れ条件ごとの対応、更新ドキュメント、実行した検証、残課題を含めること。

## 8. 完了条件

AIは作業完了時に、以下を満たしているか確認すること。

- issueの受け入れ条件をすべて満たしている。
- issue外の変更を含んでいない。
- 関連ドキュメントが更新されている。
- テストが追加または更新され、必要な検証が実行されている。
- アーキテクチャ、API仕様、型定義、Infrastructureの変更漏れがない。
- 未解決事項がある場合、残課題または別issue候補として明記している。
